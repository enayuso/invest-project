# 분봉/틱 백테스트 인프라 구축 계획

> **상태(2026-10-02 문서 정리 메모)**: **보류 중인 설계 문서**(폐기·완료 표시가 아니다). 단타(스캘핑) 백테스트 인프라 일부(`app/backtest/scalping_harness.py`, `fill_simulation.py`, `minute_candles.py`, `scripts/*minute*`)는 이 문서를 근거로 코드가 존재하지만, 운영 시스템은 스윙 전략이며 단타는 "살아있는 신호 없음"으로 보류돼 있다(`handoff/knowledge/open-issues.md` D절). 코드 주석이 이 경로를 인용하므로 파일은 이동하지 않았다.

`docs/scalping-design.md` 7절에서 확인된 선행 과제 — "반응속도를 백테스트로 학습해서
정하려면 분봉 단위 백테스트 인프라가 먼저 필요하다"에 대한 구체 계획이다. 아직 착수 전이며,
이 문서는 계획만 담는다(코드 미작성).

## 0. 새로 확인된 사실 — 과거 분봉 데이터는 생각보다 확보 가능

앞서 [[scalping-feasibility-notes]] 조사에서는 "KIS는 분봉 TR 자체가 안 붙어있다"고
판단했으나, 이는 라이브용 TR(`FHKST03010200`, 당일만/30건 제한)만 확인한 결과였다. KIS
Code Assistant MCP로 추가 확인한 결과, **과거 분봉 조회 전용 TR이 별도로 존재한다**:

- **TR `FHKST03010230`(주식일별분봉조회, `inquire_time_dailychartprice`)** — `FID_INPUT_DATE_1`,
  `FID_INPUT_HOUR_1` 파라미터로 특정 과거 날짜/시각 기준 분봉 조회 가능. 실전계좌 기준
  "한 번의 호출에 최대 120건, 최대 1년치 분봉 보관"이라고 공식 문서에 명시됨.
- **미확인**: 이 TR이 모의투자 계좌에서도 지원되는지는 MCP 문서에서 확인 안 됨(다른
  기본시세류 TR들은 통상 모의/실전 공유이지만, 이 TR은 명시적 확인 없이 가정하면 안 됨).
  → **Phase 0에서 반드시 실측 검증**.

이 발견으로 "백테스트용 과거 분봉 데이터가 아예 없다"는 이전 결론은 "있지만 검증/수집
과정이 필요하다"로 수정된다.

## 1. 목표

`app/backtest/harness.py`의 일봉 전용 시뮬레이션에, 분봉 단위 시뮬레이션 옵션을 추가해서
단타 Entry Engine의 반응속도(초/분 단위)별 수익성을 비교할 수 있게 한다. 기존 일봉 백테스트
경로는 그대로 유지(회귀 없음)하고, 분봉 경로는 별도 옵션으로 추가한다.

## 2. 단계별 계획

### Phase 0 — TR 실측 검증 (완료, 2026-07-27)

`scripts/check_daily_minute_chart_tr.py`로 모의계좌 실측 완료:

- **모의계좌 지원 확인됨** — 005930(삼성전자) 기준 2026-07-24(3일 전)와 2026-04-27(3개월 전)
  모두 `rt_cd=0`, 120건 정상 반환. `CTPF1002R`류와 달리 `EGW02006` 거부 없음.
- 응답은 최신 시각→과거 시각 역순 정렬(`FID_INPUT_HOUR_1`부터 거슬러 올라감), 1건당 1분 간격.
- **남은 확인 사항**: 정확히 몇 개월/몇 년 전까지 데이터가 살아있는지 경계값 미탐색(공식
  문서상 "최대 1년"이나 실측은 3개월 전까지만 확인). 페이지네이션 연속 호출 시 시간 겹침/
  누락 여부(연속 호출로 `FID_INPUT_HOUR_1`을 앞 페이지의 최솟값으로 계속 이동시키는 방식)는
  아직 미검증 — Phase 1 실제 수집기 작성 시 함께 확인.

### Phase 1 — 과거 분봉 데이터 수집 + 로컬 캐시 (완료, 2026-07-27)

- 캐시 저장소는 파일(parquet) 대신 **Postgres 신규 테이블**로 결정(사용자 선택) — 기존
  `app.memory.db.get_pool()` 풀을 그대로 재사용, `pending_orders.py`/`safety_switch.py`와
  동일한 `_schema_ready` + `asyncio.Lock` 더블체크 락 스키마 부트스트랩 패턴 적용.
- **신규 모듈** `app/backtest/minute_candles.py`:
  - `minute_candles` 테이블: `(ticker, trade_date, time)` 복합 PK, OHLCV 컬럼.
  - `fetch_minute_day_from_kis(broker, code, trade_date)` — `FHKST03010230`을
    `FID_INPUT_HOUR_1`을 뒤로 이동시키며 페이지네이션(최대 6페이지), 시간(`time`) 기준
    dict로 dedup, 장 시작(09:00) 도달 또는 진행 없음(earliest >= 이전 요청 시각)이면 중단.
  - `get_cached_minute_day` / `fetch_and_cache_minute_day` — 캐시 우선 조회, 없으면 수집 후
    저장(빈 날은 캐시하지 않음 — 휴장일과 "아직 미수집"을 구분하기 위함, 호출자가 사전에
    거래일만 걸러서 요청하는 것을 전제).
- **신규 CLI** `scripts/backfill_minute_candles.py` — 티커(콤마 구분)/기간(YYYYMMDD) 지정
  백필, 주말만 스킵(공휴일은 미모델링 — 빈 응답으로 자연스럽게 스킵됨).
- **실측 검증**: 005930.KS 2026-07-24 하루치 → 4회 API 호출로 381개 분봉 수집(장중
  09:23~15:30 구간 커버, 09:00~09:22 구간은 페이지 경계상 미포함 — 필요시 `_FIRST_PAGE_HOUR`/
  `_MAX_PAGES` 조정으로 보완 가능). 재실행 시 API 호출 없이 캐시에서 즉시 반환 확인 —
  캐시 히트/미스 동작 검증 완료.
- 해외(US) 분봉은 이번 Phase 범위에서 제외(국내만 우선) — KIS 해외 분봉 TR 지원 여부는 별도
  확인 필요.

**남은 항목 확인 완료 (2026-07-27, 후속 검증):**

- **09:00~09:22 커버리지 "누락" — 실은 오검(誤檢)이었음.** 실제 캐시 데이터를 직접 조회한
  결과 005930.KS 2026-07-24는 `09:00:00`부터 `15:30:00`까지 390분 전체 커버, 유일한 갭은
  `15:19~15:30`(장 마감 동시호가 구간 — 이 구간은 분봉이 정상적으로 안 나오는 게 KRX 시장
  구조상 맞음). 이전에 "09:00~09:22 미포함"이라고 적었던 건 확인 없이 추정한 오류였음 —
  실제로는 문제 없음.
- **TPS 페이싱 — 기존 스로틀로 충분함이 확인됨.** 000660.KS 2일치(2026-07-10, 2026-07-13)
  연속 백필 중 실제로 레이트리밋(HTTP 500, EGW00201류) 1회 발생했으나, `KISHttpClient._request`의
  기존 "1회 자동 재시도" 로직이 그대로 처리해 백필 자체는 실패 없이 완료됨. 대량 백필
  전용의 별도 페이싱 로직은 필요 없어 보임 — 다만 이번 테스트는 2개 티커·2일치 규모라,
  수십 종목 × 수개월 규모의 대량 백필에서도 동일하게 버틸지는 실제로 그 규모를 돌려봐야
  확실함(향후 실사용 단계에서 재확인 권장).
- **보관기간 경계값 — 약 1년으로 확인됨.** 005930 기준 2026-01-01(요청)→2025-12-30 데이터
  정상, 2025-07-27(정확히 1년 전)도 정상 반환. **2025-01-27(약 1년 6개월 전)부터는
  0건 반환**(거부 에러가 아니라 조용히 빈 배열) — "최대 1년 보관" 공식 문서 설명과 대체로
  일치. 정확한 경계일(1년 vs 1년+α)까지는 특정하지 않았으나, 백테스트 기간을 "최근 1년
  이내"로 잡으면 안전하다는 실용적 결론으로 충분.

**새로 발견된 이슈 — KIS 원본 응답 자체에 실제 데이터 갭 존재 (미해결, 리스크로 플래그):**
000660.KS 2026-07-13 백필에서 정상 범위(390분) 밖의 추가 갭 2건 발견(`12:27~12:29`,
`13:28~13:58`). 페이지네이션/dedup 버그가 아니라 **KIS가 반환한 원본 `output2` 배열 자체에
`13:28`→`13:58`로 30분을 건너뛴 행이 있음을 원시 응답으로 직접 확인**(수집 코드가 만든
문제가 아님). SK하이닉스처럼 초고유동성 종목이 정규장 중 30분간 완전히 무거래였을 가능성은
낮아 보이나, 원인은 특정하지 못함 — 후보: (a) 모의투자(paper) 서버가 제공하는 과거 분봉이
실제 시장 데이터의 완전한 복제가 아니라 일부 구간이 비어있는 데이터일 가능성, (b) 특정
가격대에서 실제로 거래가 뜸했을 가능성(낮지만 배제 못함). **이 갭의 성격을 규명하기 전까지는
분봉 데이터의 절대적 정확성을 backtest 결과 해석에 과신하지 말 것** — Phase 2(슬리피지 모델)
설계 시 "결측 분봉을 어떻게 처리할지"(이전 값으로 채움/해당 구간 스킵/거래 자체를 보류)도
함께 결정해야 함.

### Phase 2 — 슬리피지/체결지연 모델 신규 설계 (완료, 2026-07-27)

- **신규 모듈** `app/backtest/fill_simulation.py`(`app/execution/ledger.py`와 완전 분리,
  라이브 실행 경로 미접촉):
  - `simulate_fill(candles, signal_time, latency_seconds, side, slippage_bps=5.0)` — 신호
    시각+지연을 더한 목표 시각 **이후 첫 분봉의 `open`** 가격으로 체결. 슬리피지는 고정
    bp로 근사(호가 데이터가 없어 스프레드 재현 불가 — 근사치임을 명시), 매수는 불리하게
    위로/매도는 불리하게 아래로 이동(`ledger.py`의 "슬리피지는 항상 불리한 방향" 관례와
    일치).
  - `compare_reaction_speeds(candles, signal_time, side, latency_options_seconds, ...)` —
    여러 지연값의 체결가를 한 번에 비교. 7.1절의 반응속도 결정에 쓰는 실질 도구.
- **Phase 1에서 미해결로 남겼던 "결측 분봉 처리 방침"을 여기서 확정**: 없는 분을 추정해서
  채우지 않고, 목표 시각 이후 첫 실제 데이터로 체결 — 갭을 만나면 `realized_latency_seconds`가
  요청값보다 커지는 형태로 자연스럽게 드러남(`gap_inflated` 플래그). 000660.KS 2026-07-13의
  실제 30분 갭 데이터로 이 동작을 검증 완료(신호가 갭 안에 떨어지자 요청 지연 10초가 실제
  1790초로 정확히 부풀려짐).
- **실측 데모**: 005930.KS 2026-07-24, 10:00 신호 기준 지연 0s~3600s 비교 → 지연이 길어질수록
  불리한 체결가로 이어지는 게 정량적으로 확인됨(예: 5분 지연 260,000원 vs 1시간 지연
  256,500원).
- **알려진 한계**: 1분봉 단위라 같은 분 안에 들어가는 지연값(예: 5초 vs 30초 vs 60초)은
  구분 불가 — 동일 결과가 나오는 게 버그가 아니라 데이터 해상도의 한계임을 docstring에
  명시. 이보다 미세한 반응속도 차이를 검증하려면 틱 단위 데이터가 필요(이번 Phase 범위 밖).

### Phase 3 — 시뮬레이션 루프 확장 (완료, 2026-07-27)

- **신규 모듈** `app/backtest/scalping_harness.py` — `harness.py`의 일봉 루프는 그대로 두고
  완전히 별도 모듈로 분리(회귀 위험 없음, LLM 미호출, `app.execution.ledger` 미접촉).
- **`run_scalping_backtest_day`**: 하루치 분봉 리스트 + `entry_signal_fn`(pluggable)을 받아
  분 단위로 순회하며 buy/sell 시그널이 나올 때마다 Phase 2 `simulate_fill`로 실제 체결가를
  구하고, 장 마감까지 포지션이 남아있으면 마지막 분봉 종가로 강제청산(지연 없음 — 더 이상
  반응할 데이터가 없으므로).
- **`run_scalping_backtest`**: 티커+기간을 받아 Phase 1 캐시(`get_cached_minute_day`)에서만
  읽는 멀티데이— KIS를 직접 호출하지 않음. 캐시 없는 날(백필 안 됨/휴장일)은 조용히 스킵.
- **Entry Engine 로직은 여전히 미정** (`docs/scalping-design.md` 7절 item 2) — 이 루프는
  `entry_signal_fn`을 파라미터로 받는 pluggable 구조로 설계해, 실제 전략이 정해지면 그대로
  꽂아 넣을 수 있게 함. `demo_momentum_signal`(단순 상승/하락 반전마다 매수/매도)은 **루프
  메커니즘 검증 전용 placeholder이며 전략 추천이 아님** — docstring에 명시.
- **실측 검증**: 캐시된 3개 거래일(005930.KS 1일, 000660.KS 2일)에 데모 시그널 실행 →
  하루 146~184회 매매, 수익률 -11~13%. 이 손실 자체가 의미 있는 검증 결과 — "노이즈마다
  과매매하면 슬리피지 누적으로 깎여나간다"는 게 실제로 반영되고 있음을 보여줌(모델이
  죽은 채로 항상 수익만 내거나 항상 0을 내는 버그가 아니라는 뜻).

**남은 것**: Phase 4(실험 추적 스키마 확장), Phase 5(일봉 백테스트 회귀 확인 — 이번 Phase가
`harness.py`를 건드리지 않았으므로 위험 낮음), 그리고 무엇보다 **Entry Engine 실제 로직
결정**(이게 정해져야 이 루프로 진짜 반응속도 비교 실험이 가능해짐).

### Phase 4 — 실험 추적 확장
- `app/backtest/experiments.py`의 `backtest_runs` 테이블에 `granularity`(daily/minute),
  `latency_seconds` 필드 추가 여부 검토 — 기존 스키마 확장이라 마이그레이션 필요.
- `app/backtest/parallel.py`의 병렬 실행 골격은 그대로 재사용 가능할 것으로 예상(분봉
  백테스트도 종목 단위로 프로세스 분리 가능).

### Phase 5 — 검증
- 기존 일봉 백테스트 결과가 이 변경으로 바뀌지 않는지 확인(회귀 테스트).
- 소규모(종목 1~2개, 기간 1~2주)로 분봉 백테스트를 먼저 돌려서 파이프라인이 도는지만
  확인한 뒤 범위를 넓힘.

## 3. 리스크/열린 질문

- **TPS 부담**: 과거 1년치 1분봉을 종목당 처음 수집할 때 호출 횟수가 큼(하루 ~4~5회 ×
  거래일수). 여러 종목을 한 번에 수집하면 모의계좌 TPS(추정 ~2건/초)에 바로 걸릴 수 있어,
  최초 수집은 별도의 저속 배치 작업으로 분리하는 게 안전.
- **모의계좌 TR 지원 미확정** — Phase 0 결과에 따라 이후 전체 계획이 바뀔 수 있음(만약
  모의계좌 미지원이면 실전 계좌로만 수집하거나 다른 벤더를 검토해야 함).
- **체결지연 모델의 정확도 한계** — 분봉 데이터만으로는 호가 스프레드/실제 체결 슬리피지를
  정확히 재현할 수 없음. 이 한계를 인지한 채로 "상대적 비교"(반응속도 A vs B 중 어느 쪽이
  더 나은가) 용도로만 쓰고, 절대 수익률 추정치로 과신하지 않아야 함.
